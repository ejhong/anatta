## 2. Can an unscreened or failed declaration reach training or the gate quietly? Can a failure pass documents through?

No, on both, by construction:
- Selection admits only candidates with a final record that passes the keep rule; a document with no record, a non-final record (a stopped pass), a failed or unparsed record, or any label is never passing, and a stop returns before anything is written.
- `::sets` re-derives the same requirement from the files on disk for every kept declaration's current text and refuses otherwise; `train_arms` needs the sets; AS REGISTERED re-derives it again at the grade and also ties each adapter to the manifest it was trained under.
- The gate cannot see an unscreened declaration without failing: a sampled declaration with no final record stops it, and a manifest without a screen record or a screen.jsonl that is not the sealed file stops it before anything is asked (1172-1180).
- A screening failure cannot pass documents: failed and unparsed records never satisfy the keep rule; an outage trips the streak (20 in a row, loud and resumable) or the 1% rule; a format drift that leaves verdicts unparsed does the same. The one failure a screen cannot detect is a judge that answers "clean" for everything; the gate's neutral half still asks 50 neutral documents afresh and would stop on a judge that echoes the prompt's example answer (mentions_rule true), and the first gate's 100 verdicts show this judge is not of that kind.
- The seal is a prefix seal (README 37). Appended records cannot change the training set's justification: every kept document already has a final record inside the sealed bytes, and the first final record per key wins.

## 3. The implementer's worries

- **(a) The smoke is unscreened and the first real screen calls come at --go with 24 workers.** Keep the smoke unscreened (the design says it isn't judged) but lower screen.workers from 24 to 8 (config.json:87). The reason is not correctness but the drop budget: a 429 burst at 24 concurrent calls can fail a document's four tries (2, 4 and 8 s of backoff), and a completed pass finalizes those as failed, so transient rate limiting would drop documents deterministically and spend the registered 5% on nothing; at 8 workers the gate did 150 calls in 27 s with no failure, and 10,400 calls take about 30 minutes against a run of several hours. Twenty smoke declarations could not exercise 24-way concurrency anyway. This is the one change I would make before the re-freeze; config.json is not a frozen file, but its sha goes into the manifest, so set it before the build.
- **(b) A drop-rate stop repeats on every rerun.** Correct and intended: its verdicts are final, so proceeding requires a registered threshold (SCREEN_DROP_MAX, declared_core.py:905, a frozen file) and a re-freeze, which `freeze --again` allows while no set exists. Add that sentence to README point 45.
- **(c) --go stops if D30k has already started.** Accept: D30k can only have started by hand, and a skip file beside a started D30k would be false.
- **(d) The skip-reason check in AS REGISTERED.** Accept: it pins the skip to the registered decision and costs nothing.
