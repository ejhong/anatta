**Verdict: ready with changes.** The design is the right shape: same code, two scorers, same inputs, judge-free, with a gross anchor on the side; the unit and the two sets are well chosen, and every number in the registration that I could recount reproduces. What is missing is what makes a fail readable: the disagreement causes are not pinned down beyond "timing or comparison", one bad pair can fail the 99% band on its own, and two facts in the registration are wrong (the lab's token cap; what the C6c files are). Changes 1-5 belong in the registration before launch; 6-12 are pins for the code check and the card.

## Changes, ranked

**1. Pre-register the cause buckets, the known rule differences, and a tight band for the unexplained bucket.** Registration: "for each disagreement, both scorers re-run with loose time limits ... If they then agree, the cause is timing; otherwise it is the comparison." Two causes are not enough to localize a fail, and the loose re-run has two defects at commit 6eb1e19: (a) `untrusted_check`'s whole-process timeout is `min(os.getenv("EVALPLUS_TIMEOUT_PER_TASK", 60), sum(time_limits)) + 2`, so with `min_time_limit=60` the per-input limit is 60 s but the whole run is still capped at ~62 s; (b) setting that env var breaks the call (`os.getenv` returns a str, `min(str, float)` raises TypeError), so the cap cannot be raised without patching. Fix: five buckets, each decidable from data the check already has. *Timing*: both loose runs agree (repeat the loose runs 3 times; "timing" only if all three agree, else "unstable", counted as a disagreement). *Environment*: our harness output is `["raised", "MemoryError"|"ModuleNotFoundError"|"RecursionError"|...]` on the failing input, or EvalPlus's side hits a guard ours lacks (`builtins.open`, `os.getcwd`, `os.chdir`, `exit` are set to None by `reliability_guard`; its memory limit is 4 GB on RLIMIT_AS, DATA and STACK, ours 1 GB on AS only). *Known rule difference*, listed now, with the direction: numpy scalars and any non-builtin return type (ours `unsupported` fails, EvalPlus's `==` may pass; 1 of the 9,441 samples mentions numpy); complex vs float (`(1+0j) == 1.0` is True in Python, False under canon; only pairs with complex outputs); `__eq__` on the output (EvalPlus trusts it, ours never calls it; the hack detector marks these overfit anyway); set_eq tasks with float outputs or a task atol (EvalPlus falls back to `np.allclose` on the ordered lists, ours stays exact on the set forms). *Oracle*: the two reference sides differ on that input (see change 2). *Unexplained*: everything else, read by hand. Keep the overall ≥99% band, and add: unexplained disagreements at most 1 in C6a and at most 9 in C6c (0.1%); more than that is a scorer defect whatever the overall rate says, and a timing-only miss of the 99% band is a policy difference, handled by the registered re-scoring (EvalPlus's same-inputs verdicts already exist for every sample, so that consequence is free).

**2. Add a step 0 on the oracle, and a per-pair reading.** Registration: "the recorded verdict and EvalPlus's same-inputs verdict agree on at least 99% of the stored samples." Samples are concentrated: the 69 held pairs were read 36 times, so the per-pair count runs to 173 (mbpp_223), 24 pairs hold ≥94 samples, and 44 hold ≥50. One pair whose reference misbehaves in one harness (nondeterminism, a timing-marginal reference: mbpp_583 alone holds 80 samples at 1.02 s) fails the band by itself while saying nothing about the comparison code. Fix: before any verdict is compared, run `trusted_exec` on each pair's reference and require `canon()` of its outputs to equal `reference_outputs(pair)` on all 18,267 hidden inputs, and (cheaply) to match the parquet module's stored `results` under `evalplus_match`; a pair that fails is an oracle fault, its samples leave the graded count and are reported. Then report disagreements per pair, the share held by the top 3 pairs, and the direction (ours passes/EvalPlus fails = ours lenient, the direction that inflates solve rates; the reverse deflates them). A pair where ≥80% of samples disagree in one direction is read as a pair fault, but comparison-cause disagreements count against the scorer wherever they sit: the 13 atol pairs (590 samples, 193 hidden-fails) and 7 set_eq pairs (224 samples, 81 hidden-fails) are exactly where rule bugs would show, and they must not be excusable as "pair faults".

**3. Correct the lab facts the registration repeats.** (a) "with 1,024 new tokens as in the lab's reads": wrong. The reads go through `modal_durability` → `modal_retreat2.evaluate_adapter` with `MAX_NEW` from `modal_common`, which is `(512, 384)` (512 new tokens on the first reply, 384 after); `E1_MAX_NEW = 1024` is the erosion data's cap. 1,024 is fine for C6a, but say so, and record the share of replies that hit the cap. (b) "Every episode in the lab's read files": the sft source (8,050 episodes) is 3,087 from the 12 held-out reads plus 4,963 from Stage A's sampling pools (`sft/{koan,koan_cut,koan_glimpse,noexit}/episodes.jsonl`), which are training-data samples, not reads; say "read and sampling files". (c) The facts file counts 76 files; I find 67 files whose records carry pair/impossible/outcome/replies, of which 60 contribute (the told pools contribute 0 graded solvable episodes). Nine are byte-duplicates: `sft/koan_s{0,1,2}/heldout.jsonl` = `durability/reads/start/koan_s*` = `start_gate/koan_s*`, and `sft/koan_cut/episodes.jsonl` = `sft/koan_glimpse/episodes.jsonl`. The dedupe absorbs them, but the card must list the files by path and hash. (d) Replies are stored truncated at 3,000 characters (`player.REPLY_CHARS`); no graded last reply reaches it (max 2,669), so extraction is unaffected. State it and assert it in the samples script. (e) The "21,070 / 9,441 / 367 / 71.9% / no sample with two verdicts" numbers reproduce exactly in my own recount (no lab code imported).

**4. Make the timing comparison machine-readable.** Registration: "Our limit is one 20-60 s budget"; "Scoring runs one sample per CPU core". In practice the budget is 20 s for every pair: references run ≤3.35 s at build, so 4× never clears the floor unless a container is slow; EvalPlus's limit is the 1 s floor on nearly every input (references take milliseconds). Both floors are absolute, so near-threshold verdicts move with the CPU. Fixes: record on the card the CPU model, Modal cpu/memory, worker count, Python and numpy versions, the per-pair budgets actually used (`reference_outputs`'s `took`) and EvalPlus's `ref_time`; run with workers = cores and nothing else on the container; repeat timing-attributed disagreements 3 times (change 1). Two facts for the odds: the lab's recorded verdicts were scored with 16 threads on 8 CPUs (`Player.play(workers=16)`), i.e. under contention; and 2,221 of the 9,441 samples recur in 2+ episodes (1,007 across sources, ~11,600 repeated episodes in all) with zero verdict conflicts, which bounds contention flips on repeated code at well under 0.1%. Timing is unlikely to be what fails C6c; pair faults and rule edges are.

**5. C6b: single-source anchor, band off-center.** Registration: "Anchor: 67.7 ... The band is the plan's 8 points either side of 67.7"; "Expected about 70". Verified: AceCoder Table 4 Baseline row 81.7 / 73.2 / 79.4 / 67.7 (BigCodeBench 45.6/16.9/38.4/14.2, LCB 29.0, avg 49.6), "each benchmark's default setting, which is greedy sampling most of the time"; provenance unstated, but its HumanEval 81.7 against Qwen's own 84.8 shows it is AceCoder's own single run. The EvalPlus leaderboard has no Qwen2.5-7B(-Instruct) row (only Qwen2.5-Coder-32B-Instruct, 77.0), Qwen's Table 8 gives MBPP 79.2 and no MBPP+, and I found no other published number. So 67.7 is one run on one harness. Our prompt shows all three base asserts plus the signature where EvalPlus shows one assert; that is a real pull up (3-6 points, output format is the main MBPP+ failure), so expect 70-74. [60, 76] then has only 2-6 points of headroom above expectation while allowing 10 below. Center it: [62, 78], n = 368 (binomial SE 2.4). Also state that C6b uses our extraction (first fenced block via CODE_RE) not EvalPlus's `sanitize`, and report replies with no fence, with >1 fence (5% of the lab's graded replies had >1), syntax errors, and cap hits, so a miss can be read. 75% is fine.

**6. The full-set gap needs a reporting rule and a cheaper run.** Registration: "the gap to the full set ... and how much it would lower the solve rates" (reported). The 368 tasks have 39,828 inputs (median 108, max 150 per task); the hidden samples cover 18,267 (46%), and the >1,000-character inputs, the ones built to catch wrong and slow solutions, are excluded by design. This is the one number that can change what "solved" means on the page, so register: the page carries the gap whenever it lowers any reported solve rate by ≥2 points, per arm (a trained arm can learn sample-passing shortcuts), weighted by episodes as well as by unique samples (the episode-weighted solved share is 79.9% vs 71.9% by sample). Run the full set only on samples that pass the same-inputs check (a near-miss fails the full set by construction); that halves the heaviest part of the job.

**7. Scope the pass.** Registration: "C6a and C6c pass: the scorer is calibrated (card C6)." What a pass shows is that the hidden verdict (execution, canon, evalplus_match, time policy) matches EvalPlus's on the same ≤50 inputs. It does not test the input sample (change 6), the visible gate (reported only), the hack detector, the release parse, or extraction. Write the page label as "hidden verdict calibrated against EvalPlus on the same inputs (card C6); solved = passes a ≤50-input sample, gap to EvalPlus's full set X points".

**8. The AST-identity rule: make it a byte rule over the section, and record the history.** Registration: "an AST comparison of those functions in the two files, docstrings removed." The things most likely to differ are module constants and harness strings (VISIBLE_TIMEOUT, HIDDEN_TIMEOUT, HIDDEN_TIMEOUT_MAX, TIMEOUT_FACTOR, MEMORY_MB, CANON_SRC, _PRELUDE, the two HARNESS strings), which a function-level AST check skips. Simpler and stronger: byte-compare the text from `CANON_SRC` to the pairs section plus the four timeout/memory constants. I did: it is identical between the library env.py and the lab's koan_env.py, and identical in every lab version that scored anything (918b296 build, bba364e review fixes, 922550e, 373eb20; the only later change was the koan_rlvr arm). The hidden-timeout scaling entered at bba364e (29 Oct 05:45), before Gate 0's dry run (05:51) and every read. `base.CODE_RE` is identical between anatta-dev (what the lab imported) and calib. The lab's `third_party/evalplus/eval__init__.py` is byte-identical to 6eb1e19 (sha256 3c833c39…). Record those hashes on the card, not just env.py's.

**9. Environment parity of the scoring container.** The lab's image is Python 3.12 with numpy 2.5.4, regex, PyYAML, jinja2, tiktoken, torch; model code runs under `python -I` with that site-packages. A sample importing a module absent from the check's image fails there and not in the lab (an environment cause mislabelled as comparison). Pin Python 3.12 and numpy 2.5.4, grep the imports of all 9,441 samples before the run and verify each is importable in the image (stdlib-only is likely: only 1 sample mentions numpy), and record `pip freeze` and what `psutil.virtual_memory().total` reports inside the container (EvalPlus's limit is min(4 GB, that)).

**10. The cheap tier is too small as written.** Registration: "C6a's stored Qwen samples are re-scored ... fails if more than 1% of verdicts change." 1% of ~260 is 2 verdicts, inside timing noise. Use the 9,441 C6c samples (the lab's own code, ~1 CPU-hour), compare against the stored EvalPlus verdicts, and exclude flips the loose re-run attributes to timing.

**11. Pins for the code check.** `untrusted_check` forks a `multiprocessing.Process`; do not call it from a thread pool (fork from a threaded parent), use one worker process per core. Parse `pair.hidden` for EvalPlus with the harness's own restricted eval (`inf`, `nan`, `set`, `frozenset`; 7 pairs use `inf`, none use calls), so both sides see the same objects. Pass `entry_point=pair.entry` so EvalPlus's by-name set-eq dispatch fires (verified: the 7 set_eq pairs are exactly the EvalPlus names present; Mbpp/249 is not in v0.2.0's 378; no special-oracle or not-none entry survives). For the full set use the parquet module's `inputs` (base + plus; the visible asserts' inputs appear in it) with `trusted_exec` for expected values, and treat a reference that raises or hangs on a full-set input as "unreadable" for that task. `trusted_exec` deep-copies inputs and times each with `time.time()`; `unsafe_execute` does not copy but receives fresh pickled inputs, so input mutation is not a confound. Run `trusted_exec` once per pair, as EvalPlus caches ground truth. The calib/instruments branch has no `calibration/` folder yet; C1's probe path lives on calib/model-check.
