## The three oracle-fault pairs

The files support "order of set-built outputs", strongly, and not "different answers". The per-row files record only the indices that mismatched, not the two outputs, so this is an inference, but it is the only one consistent with the records:

1. All three are set-equality pairs (atol 0, set_eq true, among EvalPlus's by-name set tasks), and each reference builds its output from a set, as the pair file's reference text shows: mbpp_2 `tuple(set(a) & set(b))`, mbpp_579 `tuple(set(a) ^ set(b))`, mbpp_769 `list(set(a)-set(b)) + list(set(b)-set(a))`. Python iterates a set of strings in an order that depends on the per-process hash seed; a set of ints iterates the same way in every process.
2. Over all 350 hidden inputs of the 7 set-equality pairs, my own set arithmetic on the literal inputs sorts them into three classes. Every set-built output holding two or more strings mismatched or was one of the two mbpp_579 inputs (16 and 48) that matched in C6a's container and mismatched in C6c's: 12 inputs, 10 flagged in C6a, 10 in C6c, union all 12. Every set-built output of two or more ints matched (77 inputs, including 21 on mbpp_111 whose reference is also set-built). Every output with fewer than two elements matched (order moot). mbpp_7, mbpp_140 and mbpp_232 have ordered references or no strings and all matched.
3. The parquet's stored results match the lab's reference outputs under evalplus_match with set equality on all 50 inputs of each pair (stored_mismatch empty), so the lab's reference has the right elements; trusted_exec ran the same deterministic set arithmetic on literals the 13:10 entry found identical as objects.
4. The mismatch set changed between the two containers (8 against 10 on mbpp_579), which a content difference could not do and a per-process hash seed does.
5. No verdict depends on it: both scorers compare these pairs as sets, and none of the 59 C6c samples (all recorded solved, 221 episodes) nor the 2 C6a replies disagrees with EvalPlus. Kept in, C6a would read 293/293 and C6c 9,430/9,441 (99.88%), the same verdicts.

The exclusion is right under the registered rule (canonical equality on every input). Note for later: step 0's own test is order-sensitive on pairs whose registered comparison is order-insensitive, so it will fail these three pairs on most runs; a step 0 that compared under the pair's own rule would have kept them.
