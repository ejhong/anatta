## (a) The diagnosis is right, and the reload is safe there

- Right. A container sees the volume's committed state as of its own start or its last reload; Modal's commit docstring makes a commit "available to other containers", which they see on reload (or when they start). finetune reads data.json, train.pt and, with init, the adapter from the volume. The first wave's five containers started after build_sets committed the sets, so they saw them; Dseq_s0 was the only call that read something committed during the same app run, and Modal handed it a warm container from the first wave. modal_durability.py already guards exactly this at 464 and 609 ("a warm container may hold an older view of the volume"); finetune lacked it because Stage A never read a same-run commit.
- Safe. Modal: reload "makes the latest committed state available", "any uncommitted changes ... may implicitly be committed when reloading", and it "will fail if there are open files". At that line no volume file is open (append_jsonl opens and closes per record, modal_common.py:141-145; the src reads come after; the weights come from the cache volume, not runs). Nothing of this call has been written yet, and a reused container's previous call ended with runs.commit() after save_adapter and done.json, so there is nothing uncommitted to lose; reload discards nothing in any case. If an earlier call had died mid-way, its partial args or log could be implicitly committed, which is harmless: a rerun writes args.json anew and unlinks log.jsonl and done.json first (modal_sft.py:245-247). Limiting it to init != "new" keeps Stage A's path identical in behavior; an unconditional reload would be equally safe (a fresh container's reload is a no-op). Either is fine.
